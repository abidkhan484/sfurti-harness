# Build the Sfurti Bangla content production and publishing harness

Status: ready-for-agent

## Problem Statement

Sfurti needs a dependable way to keep its Facebook Page supplied with useful Bangla content for Bangladeshi parents of children aged 3–15. Finding suitable source videos, checking permissions and claims, selecting excerpts, producing readable Bangla media, reviewing edits, and scheduling a varied daily package currently require a coordinated workflow that does not exist in this project.

The operator wants automation that follows Sfurti's mission of meaningful effort, curiosity, creativity, problem-solving, and child agency. Popularity, screen-free branding, or a credible-sounding speaker cannot substitute for mission alignment or supported claims. The system must avoid repeating source segments, preserve editing history, and keep working through ordinary process failures and provider limits without duplicating posts.

The operator also needs a large content library, at least 90 days of approved content with assigned posting times, configurable daily counts, private Telegram access, and a filesystem CSV containing the complete upload queue. Building a large reserve must not increase the daily posting frequency or consume provider capacity without bounds.

## Solution

Build a single-machine Node harness that coordinates separate workers for discovery, content production, review, planning, and publication. Use Codex SDK initially through a replaceable LLM Strategy, with external media tools and Hermes behind their own adapters. Persist structured state in SQLite and media in an organized filesystem library.

Produce Bangla-first Reels from cleared YouTube sources, reusable branded mission images, and useful text posts. Independently review every artifact, allow at most three total versions, and automatically approve only passing content. Populate a persistent library from which the scheduler selects eligible unpublished items and assigns random times inside posting windows researched once during setup.

Plan at least 90 days ahead using actual approved artifacts, continue beyond that floor when capacity permits, and submit posts to Facebook when their dates become eligible. Keep local planning, Facebook-confirmed scheduling, and publication separate. Maintain an upload-queue CSV and expose additional custom requests, results, status, pause, and cancellation through a private Telegram bot conversation.

## Implementation Decisions

- **Current foundation:** the project contains requirements, a domain glossary, architecture decisions, configuration examples, and a Codex SDK dependency. There is no implemented harness, persistent schema, worker infrastructure, or existing test suite to extend.
- **Orchestration:** a main Node process runs on one machine and coordinates separate worker processes. The coordinator owns workflow state, limits, dependencies, leases, retries, and validated result handoffs. Hermes and daily triggers invoke the same application boundary.
- **Separate lifecycle ownership:** production fills the content library; local planning allocates eligible content to dated packages; the Facebook adapter submits and reconciles remote actions. These are separate operations so remote submission windows and failures do not force content regeneration.
- **LLM Strategy:** use Codex SDK first. Keep provider-specific threads, events, authentication, execution details, and errors inside an adapter. The application contract accepts task purpose, mission version, evidence references, a required structured-output schema, and execution controls, and returns a validated result or classified error with provider metadata and available usage information.
- **Capabilities and limits:** provider adapters distinguish reported remaining allowance from per-task usage and represent unavailable capacity as unknown. Enforce configurable conservative concurrency, workload, timeout, and backoff settings; pause on limit errors and prioritize immediate work over reserve generation. Do not silently discard evidence unsupported by a replacement provider.
- **External tool boundaries:** discovery, media inspection, editing, local transcription/dubbing, image rendering, Facebook, and Hermes use replaceable adapters. The intended editor orchestrator can guide editing tools but cannot approve its own output or override code-enforced restrictions. Validate external repository identities, installation requirements, and workflow compatibility during setup; do not assume their default approval/checkpoint behavior satisfies this design.
- **Configuration:** daily counts default to three videos, one image, and one text post. Accept nonnegative integers and allow zero to disable a type. Use a configuration file with explicit environment overrides. Topics, language/age labels, trigger times, storage locations, posting spacing, and operational limits are configurable.
- **Configuration timing:** seal today's snapshot when its first daily job starts. Future local plans remain revisable. A topic/count change preserves today's snapshot and Facebook-confirmed schedules, rebuilds future local plans, retains artifacts, returns displaced items to the library, and refreshes the queue export. Reconcile uncertain remote submissions before treating them as safe local changes.
- **Audience and mission:** serve Bangladeshi parents of children aged 3–15 with general and age-specific content. Use configurable editorial age labels with relevance-based selection rather than fixed per-age quotas. Apply the shared mission to every LLM stage, including keyword generation, framing, translation, image/text creation, editing, and review. Preserve child agency and reject the mission's hard stops.
- **Discovery:** generate structured Bangla-first keyword batches with topic, language, intent, and mission provenance. Store each keyword and its query-to-source matches. Deduplicate sources by YouTube identity and enrich useful metadata. Qualify actual content, relevance, credibility, permission, and source context before using popularity as a secondary signal. Practical relevance to Bangladesh takes precedence over creator location.
- **Permission:** retain promising uncleared sources as pending. Register an authorized source file and permission evidence, scope, attribution, restrictions, and expiry where relevant. Discovery and LLM suitability decisions do not create reuse permission. Preserve permission/source lineage through editing and publication.
- **Reels:** generate vertical 9:16 content lasting 30–60 seconds with readable Bangla captions. Prefer original Bangla; allow accurate Bangla dubbing of unusually valuable foreign sources. One Reel uses one source video, potentially with multiple intervals; every Reel in the required daily package has a different source. Add distinguishable Sfurti hooks/prompts without changing the source's meaning.
- **Source segments:** retain start/end positions relative to the original video and their mapping into output versions. Reserve overlapping intervals atomically across daily and custom work. Mark segments used at approval. Different unused intervals can be eligible later; explicit manual reuse remains possible. Retain failed-attempt history so rediscovery cannot bypass an exhausted review allowance.
- **Images and text:** use a reusable branded mission-image layout and rotating Bangla copy. Text posts offer a practical parent-child activity or thoughtful prompt with age framing when relevant. Local rendering and Bangla-capable fonts should provide reliable text layout; newly generated AI illustrations are not required.
- **Review:** an independent reviewer inspects actual artifacts and supporting evidence. Evaluate mission, factual support, preserved context, age relevance, Bangla fidelity/readability/intelligibility, and media usability. A credible speaker or a high aggregate score cannot cancel a failed hard requirement. Missing evidence produces rejection rather than a confident guess.
- **Review evidence:** the installed Codex SDK exposes text and image input, not native audiovisual input through its current public input type. Supply timestamped frames, transcripts, technical checks, and suitable audio-inspection results through media tools. Record coverage and limitations; sampled evidence cannot be represented as exhaustive video/audio validation.
- **Correction contract:** review findings identify the artifact version, affected time range or text/image location, failed criterion, supporting evidence, precise correction, and acceptance condition. Every content type has at most three total versions: initial production plus two corrections. Retry/restart cannot reset that allowance. Exhausted work remains failed; manual retry is separately recorded, and the loop does not automatically substitute another source.
- **Deterministic restrictions:** enforce schema validity, permissions, attempt limits, file validity, source diversity, and duplicate/ownership rules in code. Source transcripts and other external content are untrusted data, not instructions capable of changing tools, mission, or permissions.
- **Library planning:** select approved, unpublished, topic-relevant items using saved tags and review results; prefer older eligible items while preserving variety. An artifact already allocated to a future post cannot be allocated again accidentally. Custom work remains separate from recurring quota accounting.
- **Planning coverage:** maintain at least 90 days of complete, eligible packages backed by approved artifacts with assigned times. At default counts, this requires 270 clips, 90 images, and 90 text posts. Empty topics and unmatched aggregate totals do not count; report incomplete dates and actual coverage. Continue above the floor when provider capacity, storage, and configured limits permit.
- **Triggers and priorities:** morning opportunities occur at 06:00, 07:00, and 08:00 Asia/Dhaka. Skip overlapping daily work, recover failed ownership safely, and resume missing stages. Missed triggers wait for the next opportunity without accumulating historical daily jobs. Background production continues beyond morning hours and yields to daily shortages and explicit custom work.
- **Posting windows:** perform internet timing research once during setup and retain evidence, date, timezone, and limitations. The runtime tool draws and persists random times within saved windows and respects configured spacing. It does not repeat research or automatically learn/change the windows. A configuration that cannot fit its posting quota must report a conflict rather than silently ignore spacing.
- **Posting states:** distinguish approved artifacts, locally planned posts, Facebook-confirmed schedules, and published posts. Plan distant dates locally and submit when Facebook permits. Production completion depends on ready artifacts with local times, not immediate acceptance of distant dates by Facebook. Track remote identifiers and reconcile uncertain outcomes before retrying creation.
- **Late and failed delivery:** move late-ready content to the next feasible slot or retain it for a future day and report the shortfall. Retry publication independently of content generation. Pausing new scheduling and cancelling selected future posts are distinct operator actions; neither deletes source media or artifacts.
- **SQLite schema:** persist daily plans/configuration revisions; jobs, tasks, attempts, leases, and errors; keyword batches and keywords; unique source videos and metadata; keyword/source matches; permissions; source segments; artifact versions and artifact/segment relationships; review evidence and decisions; posting windows; and posts with origin, selected time, remote identity, and state. Large files remain in filesystem storage with stable identifiers and integrity references. Verify API metadata refresh/retention obligations during integration.
- **Filesystem organization:** separate authorized sources, permissions, generated videos/images/text, artifact versions, queue exports, and backups. Keep readable metadata in structured records while using stable artifact/source identities in storage. Retain published output, failed versions, and sources initially without automatic deletion; offer reports and explicit cleanup previews, and pause generation on insufficient space.
- **CSV contract:** every upload-queue item appears in a UTF-8 filesystem CSV. Include queue ID, artifact ID, content type, topic, age segment, file path, caption or text, source video IDs, scheduled time, timezone, status, Facebook post ID, publication time, and last error. Quote Bangla/multiline content correctly and retain terminal rows. Exact source intervals remain in SQLite.
- **CSV synchronization:** SQLite owns queue state; the CSV is a regenerable projection rather than a command-import interface. Refresh from committed state with complete temporary output and atomic replacement, retry failed exports, and report stale output. No cross-resource atomicity is assumed between SQLite and a filesystem export.
- **Telegram/Hermes:** use a private bot conversation restricted to a configured operator. Support custom creation, explicitly requested custom scheduling, source registration, status, artifact retrieval, pause/cancel, and retry. Send daily selected content, custom results, and actionable failures; summarize reserve work. Custom requests never change default topics/counts or satisfy daily requirements.
- **Installation and maintenance:** install external projects as subrepositories and document explicit manual updates, compatibility checks, and rollback. Do not update upstream dependencies automatically or while their jobs are active. Keep secrets outside documentation and queue exports. Provide setup, operation, provider/tool checks, backup/restore, storage, and recovery instructions.

## Testing Decisions

- **Confirmed primary seam:** test through the harness application-command boundary shared by scheduled work and Hermes. Use real temporary SQLite and filesystem storage with controlled fake providers, media tools, Facebook, delivery, clock, and random source. Observe command results, artifact/queue state exposed through queries, CSV, notifications, and externally issued actions. This keeps one principal behavioral seam rather than tests coupled to each worker's implementation.
- **Good tests:** assert consequential external behavior and invariants, not private methods, SQL statement order, exact prompt wording, internal function calls, or a renderer's implementation. Control asynchronous completion and time so failure/restart cases are reproducible. Exercise actual orchestration and persistence rather than replacing the system under test with mocks.
- **Prior art:** there is no existing test suite or implemented application seam in the current project. Introduce this boundary at the highest practical level and document it for maintainers. Preserve the established ADR separation between orchestration/provider adapters and production/planning/publication.
- **Configuration and plans:** verify overrides, invalid/zero counts, all-disabled behavior, today's immutable snapshot, and rebuilding future local plans without cancelling Facebook-confirmed schedules or losing displaced artifacts.
- **Discovery and evidence:** verify keyword/source relationships, source deduplication, stored context, pending permission eligibility, rejection of unsupported claims, and handling of missing audiovisual evidence. Structured-output conformance alone must not imply substantive review success.
- **Production and review:** verify all content types, three total versions, precise correction handoff, automatic approval only on passing review, terminal failure retention, and explicit manual retry without hidden resets or candidate substitution.
- **Source identity and concurrency:** run concurrent scheduled/custom attempts against overlapping source intervals, verify one owner, preserve approval-based use history, allow distinct eligible intervals, and enforce different sources within daily packages including reserve selections.
- **Recovery and limits:** simulate a worker crash, abandoned lease, provider rate limit, unknown quota, transport retry, and storage exhaustion. Assert bounded work, resumption of successful stages, priority for immediate work, and no duplicated artifacts or reset correction counters.
- **Coverage and scheduling:** verify complete 90-day coverage requires actual approved artifacts and per-date counts; partial type/date gaps are visible; scheduled unpublished content counts once; generation can continue beyond 90 days; and library size never changes daily quotas. Verify saved windows, persisted random choices, spacing conflicts, late readiness, and no repeat research.
- **Publication:** test local plans beyond the remote scheduling window, submission becoming eligible, distinct local/remote/published states, cancellation and pause, and a remote success followed by a client timeout. Reconciliation must prevent duplicate creation and must complete before a configuration change rearranges an uncertain post.
- **CSV and storage:** round-trip multiline Bangla captions and terminal states, verify all queue items and artifact references appear, interrupt an export, and rebuild from SQLite without losing publication work. Verify cleanup preview and storage alerts preserve referenced artifacts.
- **Telegram/custom work:** verify operator authorization, custom delivery without publication by default, explicit custom scheduling, independent daily accounting, summarized reserve notifications, status, and media retrieval.
- **Focused live adapter checks:** separately verify provider structured output and evidence capabilities, actual Bangla rendering/transcription/dubbing on representative samples, editor artifact output, and Telegram delivery. Test Facebook only with established credentials and an explicitly scoped test publication. These checks establish compatibility and media quality; they do not replace deterministic application-boundary tests.
- **Completion bar:** the observable workflow must survive the above failure scenarios, preserve mission/permission requirements, maintain traceable outputs and queue history, and produce a verified end-to-end sample before recurring production/publication is enabled. No implementation tests have run yet because the harness does not exist.

## Out of Scope

- Selecting a specific Montessori product, setting prices, holding inventory, running paid ads, or implementing commerce/fulfilment.
- Multi-machine distributed execution, multiple-page account management, or a public multi-user control interface in the initial version.
- Automatically publishing custom content without explicit scheduling intent or counting it toward recurring requirements.
- Unpermitted source acquisition/reuse, automated creator outreach, or using an LLM's judgment as permission evidence.
- Relaxing claim support, mission alignment, language quality, source diversity, or review limits merely to fill a daily quota.
- Automatic dependency updates, unbounded provider work, or silent switching to paid external audio services.
- Daily posting-time research, automatic window optimization, or a promise that aggregate internet timing evidence proves optimal Bangladeshi-parent engagement.
- Direct CSV edits controlling the running queue, automatic artifact deletion, and automatic edits to already published Facebook posts.
- Fresh AI illustrations for every mission image and a guarantee of native exhaustive audiovisual review through the initial SDK.
- A guarantee that 90 days of approved content exists immediately or can be produced when permission, source quality, provider capacity, or storage is insufficient.

## Further Notes

- The user confirmed the consolidated product requirements, application-command testing boundary, local Markdown tracker, and canonical triage vocabulary. This spec is published in that local tracker with status **ready-for-agent**.
- The harness is not implemented. Tracker publication records implementation-ready requirements; it does not claim that the runtime, tests, credentials, or external integrations already exist.
- Setup must establish actual provider/tool authentication, verified upstream repositories and versions, Facebook Page/app eligibility and limits, Telegram operator identity, brand assets, Bangla-capable rendering/audio tools, one-time researched posting windows, spacing, workload values, storage thresholds, and backup destination/cadence. These are implementation/setup checks within the agreed behavior, not another product interview.
- Keep the mission reference stable and principle-based. Persist mission/provider/configuration provenance with decisions so later changes remain explainable without treating temporary business choices as permanent mission rules.
